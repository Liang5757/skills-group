# 技术交底书写作指南

## 目录

- 基本信息与名称
- 背景技术
- 要解决的技术问题
- 发明具体实现
- 发明保护要点
- 其他相关文档
- 常见退化写法

## 基本信息与名称

建议文档名为 `技术交底书-方案名称-第一发明人`。发明人按实际技术贡献排序，不按职级排序。记录提案人、部门、交底书撰写人和可用联系方式；对外输出前移除无必要的个人敏感信息。

名称优先采用“一种 + 对象/场景 + 核心技术类型”的中性表达，例如“一种基于操作序列重构的视图诊断方法及系统”。只选择正文已有充分技术内容支撑的主题类型，不为扩大表面范围而机械追加装置、设备或存储介质。避免产品名、营销词、效果承诺和过窄的具体库名。

## 背景技术

背景技术同时承担“让读者理解领域”和“建立可比较基线”两个任务。推荐顺序：

1. 说明应用场景、关键对象和必要术语。
2. 描述最接近现有方案的方法步骤、系统组成或交互关系。
3. 在明确条件下说明缺陷、原因和后果。
4. 收束为仍待解决的技术矛盾。

缺陷要能由现有机制推出，例如“串行调用耗时接口导致后续初始化被阻塞”，而不是只写“效率低、体验差、智能化不足”。不要提前混入本发明方案。

## 要解决的技术问题

先标明最主要技术问题，再列次要问题。随后用一段话概括核心方案和有益效果，形成“问题—手段—效果”映射。

技术问题应描述需要消除的技术矛盾，不直接写成产品需求。对于多个问题，逐个核对后文是否有对应技术手段；没有则删除或标记待扩展。

## 发明具体实现

这是交底书主体，详细程度应达到本领域技术人员能够据此实现。根据方案选择以下小节，通常不应省略前五项。

### 1. 术语与约束

定义主体、对象标识、状态、输入输出、运行环境和关键约束。英文术语首次出现时给出中文名称、英文全称与简称。

### 2. 整体架构

列出装置、服务、模块或层级，说明各自职责、部署位置、调用方向和交换的数据。区分采集、处理、决策、执行、存储和展示等职责，避免模块名称只有“智能模块”“处理模块”等空泛词。

### 3. 核心方法流程

用 S1、S2… 描述步骤。每一步尽量回答：

- 谁在什么条件下触发
- 接收什么输入、读取什么状态
- 执行什么技术处理
- 产生什么中间结果或状态变化
- 把什么输出交给下一步
- 失败、超时、乱序、并发或资源不足时如何处理

需要时给出数据结构、字段、公式、伪代码、阈值、排序/聚合规则和状态机。具体库、协议或阈值若不是必要特征，应同时描述上位概念和替代选项。

### 4. 方法实施例

选择一个可落地场景，从初始条件开始走完整流程，并给出关键输入、时间顺序、中间状态、判断条件、输出及异常路径。实施例用于证明方案可实现，不应仅重复架构概述。

### 5. 系统实施例

把方法步骤映射为模块或装置职责，说明模块之间的连接、调用和数据关系。软件类方案可同时覆盖客户端、服务端、设备和存储介质视角，但不要在缺少支持内容时机械堆叠载体。

### 6. 附图说明

优先考虑：现有方案对比图、整体架构图、核心流程图、时序图、状态机图和关键数据结构图。每幅图包含：

- 图号与图名
- 图中节点/连线含义
- 对应正文步骤或模块
- 不看图也能理解的文字说明

### 7. 技术效果与证据

逐项对应技术问题，写清产生效果的技术原因。量化结果必须附带基线、测试环境、样本、指标定义和统计口径。预测效果与实测效果分开写。

### 8. 替代方案与边界

围绕非关键结构、器件、协议、算法、阈值、部署位置和步骤顺序给出替代。说明哪些步骤可省略、合并、并行或调整顺序，以及在什么条件下仍能实现发明目的。补充失败模式、降级方案和不适用场景。

## 发明保护要点

保护要点默认不是正式权利要求。按以下层次提炼：

1. 核心特征组合：缺少任一项就无法得到主要技术效果的组合机制。
2. 关键数据或控制关系：标识、序列、状态、触发条件、反馈关系等。
3. 可选增强：阈值、特定接口、并行策略、缓存、压缩、展示等从属特征。
4. 方法与系统映射：同一核心机制在步骤和模块两个视角下的表达。

不要只保护结果，如“提高诊断效率”；也不要只列产品功能。避免把具体厂商、框架、数据库或协议写成唯一实现，除非它本身就是必要创新点。

## 其他相关文档

列出支持理解和验证方案的原始材料：设计文档、源码入口、接口协议、实验报告、日志、架构图、流程图、演示、历史方案和关联专利点。给出标题、链接或路径及其用途，不堆放无关链接。

## 常见退化写法

- 只有行业背景，没有最接近现有方案及其步骤。
- 只有目标和效果，没有模块、步骤、数据或控制关系。
- 架构图代替正文，图中节点没有职责和交互说明。
- 把“AI、自动化、动态、智能”当作实现机制。
- 保护要点只是功能清单，未提炼必要特征组合。
- 实施例只换了业务名，没有给出具体输入、状态和判断过程。
- 编造效果数字，或使用无法复核的“显著提升”。
- 把尚未实现的设想写成已上线事实。
