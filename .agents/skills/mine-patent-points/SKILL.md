# 专利点挖掘

## 目标

把真实技术事实转化为若干边界清楚、理论可行、可继续撰写技术交底书的候选专利点。不要把“尚未实现”当作淘汰条件；要明确区分已上线、开发中、概念方案和待验证假设。

不要承诺可授权、具备新颖性或不侵权。专利性判断需要专利检索与专业法律评审。

## 工作流

### 1. 建立事实底座

优先读取用户提供的源码、架构图、PRD、设计文档、复盘、会议记录和指标。必要时追问一个最影响结果的问题，但先利用已有材料推进。

整理业务目标与使用场景、现有技术方案和数据流、约束与遗留问题、失败尝试和取舍、尚未实现但理论可行的设想，以及可证明技术效果的指标。引用文件、章节、代码位置或原话作为证据；事实不足时标记“待确认”，不要补写成既成事实。

### 2. 多路挖掘候选

阅读 [references/mining-method.md](references/mining-method.md)，至少覆盖以下路径：

1. 从现有架构和模块细节提炼非公开技术机制。
2. 从现有方案的缺点、遗留问题和难点反推新方案。
3. 从业务发展带来的新问题与未满足需求寻找方案。
4. 从开发讨论中的灵感、跨模块复用和组合方案扩展候选。
5. 从项目演进和总结中提炼策略、算法、数据结构或协同机制。

对每个高价值问题连续追问“还能怎样解决、怎样降低代价、怎样适应另一约束”。小改进可以先保留，再尝试与同一技术主线上的数据、控制或反馈机制组合成完整方案。

### 3. 形成技术闭环

每个候选必须完整回答：

- 在什么技术场景下出现什么问题？
- 现有做法为什么不足？
- 方案引入哪些关键技术特征？
- 各特征按什么顺序或关系协作？
- 为什么这些特征能产生预期技术效果？
- 哪些部分是核心必要特征，哪些是可选增强？

只有业务规则、展示文案、人工流程或抽象目标，没有具体技术手段时，降级为线索，不包装成成熟专利点。

### 4. 去重、拆分与排序

先按“技术问题 + 核心机制 + 技术效果”判断候选是否重复。一个候选包含多个可独立工作的核心机制时拆分；多个小点只有组合后才形成闭环时合并。

按技术性、差异度、效果性、完整度、证据度和战略价值各打 1–5 分，并简述依据。证据不足不等于没有价值，但应降低证据度并列出验证动作。未经检索时把差异度称为“内部初评”，不要称为新颖性结论。

### 5. 输出候选清单

按综合优先级分为 A（优先评审）、B（补证后评审）、C（暂存线索）。默认先给 3–8 个候选，使用 [references/output-template.md](references/output-template.md) 的字段。

最后补充候选合并/拆分建议、发明人待答问题、证据或实验清单、专利检索关键词（中英文、同义词、核心组件）和保密提醒。

## 质量门槛

交付前逐项检查：

- 是否基于真实材料而非泛泛脑暴
- 是否同时覆盖已实现与未实现但理论可行的方案
- 是否明确技术问题、技术手段、因果链和技术效果
- 是否把关键事实与推测分开
- 是否避免仅用“AI、智能、自动、动态”等词替代机制
- 是否给出反例、边界条件或失败模式
- 是否避免法律结论和授权承诺
